# Release checklist

The repository contains a development candidate. Source publication is separate
from distributing an iPhone binary or publishing the website. The maintainer
handles website deployment, TestFlight and App Store submission.

## Before distributing an app build

- Resolve the dependency licensing and native-binary provenance items in
  [PRIVACY-AUDIT.md](PRIVACY-AUDIT.md). A build passing does not clear these items.
  The [protocol-removal plan](PROTOCOL-REMOVAL-PLAN.md) records the restore checkpoint,
  scoped implementation, acceptance checks and rollback procedure.
- Run the checks in [BUILD.md](BUILD.md), including the public-source scan.
- Verify the Docker/Nginx RTMPS-to-HTTPS package with
  `python3 tests/integration_docker.py` on Linux with Docker, FFmpeg and OpenSSL.
- Verify real certificate issuance and renewal, exposed ports, reboot behavior
  and credential rotation on an isolated test server.
- On a signed physical iPhone, check setup persistence across reopening and updates,
  reset, invalid addresses/credentials/certificates, denied/restored permissions,
  all resolutions, continuous audio, Start/Stop, dark screen and accessibility.
- From another network, check native Safari authentication, HLS cookies/redirects,
  expand/exit, reconnect and a desktop fallback browser. Verify picture and sound.
- Check recovery from temporary connectivity and server loss with test devices.
- Have two independent self-hosters follow the setup documentation without help.
- Audit actual network traffic, stored files, logs and the final archive privacy report.
- Capture real app screenshots without server addresses, passwords or private scenes.

## Source publication

The intended repository is `itsvessy/poochcam`. Retain Moblin's MIT notice,
HaishinKit's BSD notice, attribution and the pinned dependency revisions.

1. Review the full diff, including binary assets, new files and deleted files.
2. Run `python3 tools/check_public.py` before staging.
3. Run `python3 tools/check_public.py --staged` after staging. This reads the exact
   staged blobs, not a possibly different working copy.
4. Before pushing, run `python3 tools/check_public.py --history main` to inspect
   every commit reachable from the branch being published.
5. Push only the reviewed branch. Never push private archive branches or all refs.

Signing settings belong in ignored `ios/Config/User.xcconfig`. Server state,
recordings, diagnostics, design references, build products and account handoffs
must remain outside published commits.

## Website publication

The five static pages, custom 404, sitemap and robots.txt are generated by
`python3 tools/build_site.py`. Cloudflare
Workers builds the connected GitHub repository. The root `wrangler.jsonc` selects
only `site/` as the static asset directory; no Worker script is needed.

1. Review the generated pages, support contact and privacy policy. Confirm that
   actual support-message retention matches the policy before publication.
2. In Cloudflare **Workers & Pages → Create application → Import a repository**,
   connect `itsvessy/poochcam`. Limit the GitHub installation to this repository.
3. Use project name `poochcam`, matching the Wrangler configuration, and production
   branch `main`. Keep the root directory at the repository root. Set these fields:

   | Field | Command |
   | --- | --- |
   | Build command | `python3 tools/build_site.py` |
   | Deploy command | `npx --yes wrangler@4.70.0 deploy` |
   | Preview command | `npx --yes wrangler@4.70.0 versions upload` |

   The configuration supplies the asset directory; no separate output-directory
   field or application secrets are needed. Cloudflare handles deployment access
   through the connected account. These commands pin the CLI version validated
   with this configuration; check both dry runs before upgrading it.
4. Deploy and review the resulting `workers.dev` site. Leave optional Web Analytics,
   Zaraz and other script injection disabled. Verify all five routes, notices,
   mobile layout and keyboard access. Check a nested nonexistent address: it must
   return HTTP 404 with the branded recovery page and working navigation/assets.
   Check canonical links, the sitemap and the headers configured in `site/_headers`.
5. In the Worker's **Settings → Domains & Routes → Add → Custom Domain**, add
   `poochcam.ca`. Review the website DNS change Cloudflare proposes; preserve email
   and verification records. For a redirect-only `www.poochcam.ca`, add a proxied A
   record `www` pointing to `192.0.2.0`. Under Rules, create a 301 Redirect Rule
   matching `https://www.poochcam.ca/*` with target `https://poochcam.ca/${1}` and
   Preserve query string enabled. Enable Always Use HTTPS under SSL/TLS → Edge
   Certificates. Check HTTPS and redirects, including paths and queries, on both
   hostnames.

Git integration deploys subsequent `main` pushes automatically. Review site changes
before pushing. The preview command uploads a version without changing the active
production deployment. GitHub Pages is not used, and no GitHub deployment workflow
or `CNAME` file is required. Associate custom domains with the Worker through its
settings. Do not direct the public website domain to a private camera feed.

## Support and review access

The public contact is `support@poochcam.ca`. Verify both delivery and a reply;
keep forwarding destinations and account configuration in a private handoff.
Use an isolated review server with non-sensitive test scenes and a defined budget.
Provide reviewer connection details privately in App Store Connect, never in Git.
Keep that server available through beta/review and delete paid resources afterward.

## App Store

Use the intended production bundle ID, version and unique build number. Review
current account agreements, SDK requirements, age rating, export compliance and
privacy answers. Use the verified privacy/support URLs and real screenshots.
The initial listing is free, English and Canada-only, with manual release after
approval. [APP-STORE.md](APP-STORE.md) contains draft text and reviewer instructions.

## Rollback

For website problems, use the Worker's **Deployments** tab to roll back to a
previous working version, then revert the faulty source change before the next push.
Preserve DNS and certificate settings together when reverting domain changes.
For servers, restore the saved configuration and pinned images, then verify video
and audio; credential changes also require updating the camera and viewers.
For the app, pause new distribution if needed and submit a corrected build.
Installed App Store apps cannot be remotely downgraded.
